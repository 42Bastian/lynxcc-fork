cc65 Library Overview

Ullrich von Bassewitz

An overview over the runtime and C libraries that come with the cc65 compiler, including a discussion of the differences to the ISO standard.

1. Overview

This file contains a short overview of the libraries available for the cc65 C compiler. Please have a look at the function reference for a function-by-function list. Because the function reference is not complete (we're working on that), it may happen that you don't find a specific function. In that case, have a look into the header files. All functions, that are not defined by the ISO C standard, have a short comment in the headers, explaining their use.

2. ISO C compatible library

The C library contains a large subset of the ISO C library. Functions usually are missing in areas where there are no support on typical 6502 systems. Wide-character sets are an example for that.

I will not go into detail about the ISO functions. If a function is not mentioned here explicitly, expect it to be available, and to behave as defined in the C standard.

Functions that are not available:

  • tmpfile/tmpnam

  • system and the non-standard exec: the Lynx has no shell or command processor. To run another cart image, use lynx_load/lynx_exec from <lynx.h>.

  • All functions that handle floating point numbers in some manner.

  • The ldiv function (cc65 currently is not able to return structs, by value, with a size not equal to 1, 2, or 4 bytes).

  • All functions handling wide-character strings.

  • Signals and all related functions (having SIGSEGV would be cool. :-)

  • setbuf/setvbuf

File I/O on the Lynx is read-only, because the cart is ROM and there is no character console:

  • There is no FILE object, so none of the byte-stream functions are provided. The output family is absent — fopen/freopen/fclose, fwrite, printf/fprintf/vprintf/vfprintf, putchar/puts/fputc/fputs and perror — and so is the input FILE family: fread/fgets/fgetc, fscanf/scanf/vfscanf/vscanf, fseek/ftell/fgetpos/fsetpos/rewind, getchar/gets/ungetc, feof/ferror/clearerr/fflush and fdopen/fileno. For on-screen text use tgi_outtext from <tgi.h>.

  • The only <stdio.h> functions that remain are the in-RAM string routines: sprintf/snprintf (and vsprintf/vsnprintf) format into a buffer, and sscanf (and vsscanf) parses one. Because cc65 has no floating-point support, the floating-point conversions (e E f F g G a A) are absent from all of them, and sscanf additionally rejects the wide-character conversions (S C). To stream raw bytes from the cart, use read()/lseek() on a handle from openn() (see <unistd.h> and <lynx.h>).

  • remove/rename and the name-based open/creat/close/write are not provided: cart files are ROM and are addressed by number, not by name.

  • time: Many of the supported systems don't have a real-time clock, which means that the time function is not available. Please note that the other functions from time.h are available.

Functions that are limited in any way:

  • strcspn/strpbrk/strspn: Those functions have a length limitation of 256 for the second string argument. Since that string gives a character set, and there are only 256 distinct characters, that shouldn't be a problem.

  • getenv/putenv: there is no environment on the Lynx, so these functions are not provided.

  • locale: There is no locale other than the "C" locale. The native locale is identical to the "C" locale.

In addition to those limitations, some more functions are limited if inlined versions are requested by using the -Os command-line option:

  • The strlen function works for only strings with a maximum length of 255 characters.

  • The isXXX character classification functions from <ctype.h> will give unpredictable results if the argument is not in character range (0..255). That limitation may be removed by #undef'ing the function name (when using -Os, the functions are actually macros that expand to inline assembly code, but the real functions still are available if the macro definition is removed).

3. CPU-specific stuff - 6502.h

The header file 6502.h contains some functions that make sense only with the 6502 CPU. Examples are macros to insert more or less useful instructions into your C code, or a function to call arbitrary machine language subroutines, passing registers in and out.

4. Target-specific stuff

This tree supports a single target, the Atari Lynx. The header file <lynx.h> contains calls and defines specific to the Lynx, and the hardware itself is described by <_mikey.h> and <_suzy.h>.

The header files contain

  • Defines for special keys and characters

  • Variables with a fixed address in memory that may be used to access special hardware (the MIKEY and SUZY structs). Using those variables will make your program more readable. Don't fear ineffective code when using those variables, the compiler will translate reads and writes to those structs into direct memory accesses.

  • Other routines that make sense for only the Lynx, such as cartridge and EEPROM access.

5. Reading the joypad - joystick.h

The Lynx has exactly one joypad and it is always present, so this tree replaces the generic loadable joystick driver with a small static implementation (see LYNX_JOY_SER_DESIGN.md). There is nothing to install: a single call to joy_read() returns every input the console has — the d-pad, the A and B buttons, Option 1, Option 2 (low byte) and Pause (bit 8). The JOY_*_MASK test macros are declared in <lynx.h>.

Edge detection (“was this button just pressed?”) is the caller's one-liner, since there is no longer any keyboard emulation:

now = joy_read (JOY_1);
pressed = now & ~prev;
prev = now;

The em (extended memory), mouse, conio and dbg APIs that ship with the stock cc65 library are not part of this tree: the Lynx has a flat 64 KB address space, no pointing device and no text mode, so those headers and their drivers have been removed entirely. Text output goes through the TGI bitmap-font functions instead (see tgi.html).
