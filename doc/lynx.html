1. Overview

This file contains an overview of the Atari Lynx runtime system as it comes with the cc65 C compiler. It describes the memory layout, Lynx specific header files, available drivers, and any pitfalls specific to that platform.

Please note that Lynx specific functions are just mentioned here, they are described in detail in the separate function reference. Even functions marked as "platform dependent" may be available on more than one platform. Please see the function reference for more information.

2. Building your first Hello World application

Here is a small traditional Hello World program for the Atari Lynx.

#include <lynx.h>
#include <tgi.h>
#include <6502.h> 

void main(void) {
  tgi_init();
  CLI();
  while (tgi_busy())
    ;
  tgi_clear();
  tgi_setcolor(COLOR_GREEN);
  tgi_outtextxy(0, 0, "Hello World");
  tgi_updatedisplay();
  while (1)
    ;
}

The lynx.h contains all kind of system dependent things.

The tgi.h contains the graphics functions.

The 6502.h is needed for executing the CLI() command.

As the Atari Lynx does not have ASCII characters available you need to use the Tiny Graphics Interface library for producing letters on the screen.

The cc65 compiler suite has a graphics library called "Tiny Graphics Interface". This interface has some relocatable code. In order to use this in your own program you need to load it at run time.

Unfortunately the Lynx does not have a disk drive from where to load it. Therefore you must already load it at compile time. The easiest way is to automatically link it in statically from the Lynx C library.

cl65 -t lynx -o game.lnx main.c

This will create a bootable cart image called game.lnx

3. Binary format

The standard binary output format generated by the linker for the Lynx target is a cart image. By specifying the config file lynx-bll.cfg the linker will generate BLL download compatible binary files.

It is of course possible to change this behaviour by using a modified startup file and linker config.

The bootloader used in the cc65 lynx library uses a very minimal bootloader that does not check the cart or show a title screen.

The advantage of this bootloader is that it allows creation of cart images to many common formats.

Cart sizes

Block size Rom size Description
512 bytes  128k     Standard old games like Warbirds
1024 bytes 256k     Most common format for homebrew. Also newer games like Lemmings
2048 bytes 512k     Largest games like EOTB

4. Memory layout

cc65 generated programs with the default setup run with the I/O area and the kernal enabled, which gives a usable memory range of $200 - $C037.

Special locations:

  0000 - 00FF Zero page
  0100 - 01FF Machine stack

  A058 - C037 Collision buffer
  C038 - E017 Screen buffer 1
  E018 - FFF7 Screen buffer 0
  FFF8 - FFFF Hardware vectors

The same map is shown below. With the default config (lynx.cfg) the program, heap and C stack share the RAM below the screen buffers; the __STACKSIZE__ reservation (1 KB by default) sits at the very top of that area, just under the first screen buffer:

When collision detection is enabled (lynx-coll.cfg) a 2 KB collision buffer is carved out below the screen buffers, so the usable program area and the top of the C stack move down to $A057:

Text screen

There is no conio support: the Lynx has no text mode. Text output goes through the TGI bitmap-font functions (tgi_outtext, tgi_outtextxy).

Keyboard

There is no keyboard. The Opt 1, Opt 2 and Pause switches are joypad inputs, reported by joy_read() together with the d-pad and the A/B buttons (masks JOY_OPT1_MASK, JOY_OPT2_MASK, JOY_PAUSE_MASK in lynx.h). The classic conventions Pause+Opt 1 = restart and Pause+Opt 2 = flip screen are game conventions for the application to honor.

Stack

The C runtime stack is located at $C037 (or $A057 if collision detection is enabled) and growing downwards.

Heap

The C heap is located at the end of the program and grows towards the C runtime stack.

Screen

The collision detection screen is at $A058 if it is enabled. The double buffered screens are at $C038 and $E018.

5. The C runtime stack and stack-overflow checking

cc65 programs use two independent stacks. The 6502 hardware stack lives in page 1 ($0100–$01FF, a fixed 256 bytes) and holds subroutine return addresses and interrupt state. The C software stack — also called the parameter stack — holds function parameters and local variables; it is addressed through the zero-page pointer sp and grows downwards from the top of the MAIN memory area. The amount of RAM reserved for it is the link-time symbol __STACKSIZE__, which defaults to $0400 (1 KB).

5.1. Setting the stack size

All four Lynx configs (lynx.cfg, lynx-bll.cfg, lynx-coll.cfg and lynx-uploader.cfg) reserve the stack the same way. They declare a weak symbol and then shrink the MAIN region by exactly that amount, for example in lynx.cfg:

SYMBOLS {
    __STACKSIZE__: type = weak, value = $0400; # 1k stack
}
MEMORY {
    MAIN: file = %O, define = yes, start = $0200, size = $BE38 - __STACKSIZE__;
}

The startup code (crt0.s) then sets the initial stack pointer to the top of that reservation:

sp = __MAIN_START__ + __MAIN_SIZE__ + __STACKSIZE__

so the stack occupies the top __STACKSIZE__ bytes of MAIN and grows down toward your code, data and heap. Because the symbol is weak, the default can be overridden at link time without editing the config — for example to grow it to 2 KB for a recursion-heavy program:

cl65 -t lynx -Wl --define,__STACKSIZE__=$0800 -o game.lnx main.c

Every byte handed to the stack is a byte taken from code, data and heap, so the goal is to pick the smallest value that still survives the deepest call nesting and the largest local arrays your program uses. There is no automatic overflow protection at this size — if the stack grows past its reservation it silently collides with the top of BSS/heap — unless you enable stack-overflow checking, described next.

5.2. Enabling stack-overflow checking

The compiler can instrument every function with a call to a small checking routine (stkchk/cstkchk in the runtime library). This is off by default. Turn it on for a whole build with the compiler option:

cl65 -t lynx --check-stack -o game.lnx main.c
cc65 -t lynx --check-stack main.c          # compiler invoked directly

or enable it only around specific code with the #pragma check-stack, which understands push/pop:

#pragma check-stack (push, on)
/* deeply-recursive or stack-heavy functions here */
#pragma check-stack (pop)

With checking enabled the compiler emits a jsr stkchk at every function entry (the hardware-stack check) and, for functions that allocate locals, a jsr cstkchk after the locals are reserved (the C-stack check). Each routine works against a safety margin rather than the exact limit: cstkchk treats the bottom 256 bytes of the C stack as a reserved zone and aborts once sp descends into it, and stkchk aborts when fewer than 12 bytes of the hardware stack remain. So with checking on, the effective usable C stack is about __STACKSIZE__ − 256 bytes:

If either check trips, the routine resets sp to its initial value and calls _exit(4), so the program aborts. The Lynx has no console, so there is no diagnostic message — the program simply stops — which makes this primarily a development-time aid.

Overhead. The instrumentation is cheap per call but it is paid on every call, including hot loops and recursion. Each call site costs 3 bytes for the jsr, and the routines themselves run in roughly 18 cycles (hardware-stack check) and 21 cycles (C-stack check) on the normal no-overflow path — about 40 cycles for a function that gets both. There is also a one-time cost of well under 100 bytes: the routine is linked once, plus 4 bytes of state and a start-up constructor that records the initial stack pointer. Because of the per-call tax, enable checking while debugging and stack-tuning, then build the release without it.

A practical way to size __STACKSIZE__: build with --check-stack and a deliberately generous stack, exercise the deepest call paths, and tighten the value until checking no longer aborts — leaving the 256-byte safety margin as headroom. See #pragma check-stack in the cc65 manual and the __STACKSIZE__ notes in the ld65 manual for more detail.

6. Dynamic memory allocation (the heap)

Dynamic memory is available through the standard <stdlib.h> functions malloc, calloc, realloc and free. There is no operating system beneath them: the heap is simply a window of RAM in the MAIN area (section 4), bounded below by your program's static data and above by the C-stack reservation (section 5). The allocator is the standard cc65 implementation — a first-fit free list backed by a bump pointer for fresh memory — carrying a deliberately small per-block header for the Lynx's flat 64 KB address space.

6.1. How allocation works

Five runtime variables (declared in <_heap.h>) describe the heap at any moment: _heaporg, the fixed bottom, equal to the end of BSS; _heapptr, the bump pointer marking the top of the memory touched so far; _heapend, the ceiling, set once at start-up to sp − __STACKSIZE__ ($BC38 with the default 1 KB stack); and _heapfirst/_heaplast, the two ends of a doubly-linked free list of recycled blocks. Everything between _heaporg and _heapptr has been handed out at least once; everything from _heapptr up to _heapend is still untouched.

Every live allocation carries a two-byte header that holds the block's total size. The pointer you receive points just above that header, so the raw block is always (p − 2) and the size word can be read directly from the two bytes below any valid pointer. When a block is freed and entered into the free list, those same bytes are reinterpreted as a six-byte list node (size, next, prev) — which is why the smallest possible block is 6 bytes and a 1-byte request is rounded up to it. (See LYNX_HEAP_HEADER_DESIGN.md for the full layout rationale.)

malloc() rounds the request up by the two-byte header (and up to the 6-byte minimum), then walks the free list for the first block large enough. A match is either used whole or sliced from its top; if nothing fits, the bytes are carved from the untouched region by advancing _heapptr. If that advance would pass _heapend, the request fails and malloc() returns a null pointer.

free() has a fast path: a block sitting exactly at the heap top is released by simply lowering _heapptr back over it (and if the last free-list block is now at the top, it is absorbed as well). Any other block is inserted into the address-ordered free list and merged with adjacent free neighbours, so that runs of contiguous frees collapse back into one large block instead of fragmenting. The figure below shows the resulting picture: live blocks and free-list holes below _heapptr, untouched space above it, and the C stack descending from the top of MAIN.

realloc() grows or shrinks a block in place when it is at the heap top, and otherwise allocates a fresh block and copies the data over; calloc() is malloc() followed by a zero-fill. Four cc65 extensions round out the API: _heapblocksize() returns the user-visible size of an allocation, _heapmemavail() the total free space, _heapmaxavail() the largest single block that could still be allocated, and _heapadd() donates an arbitrary buffer (for example a static array) to the free pool.

6.2. How it deviates from POSIX

This is a freestanding allocator for a machine with no operating system, no memory-management unit and a 16-bit address space, so it departs from a hosted POSIX environment in several ways worth knowing before you port code onto the Lynx:

  • No brk, sbrk, mmap or virtual memory. The heap can never grow past the static _heapend ceiling; its maximum size is fixed at link time by where BSS ends and how large __STACKSIZE__ is. Total capacity is on the order of tens of kilobytes, and size_t is 16 bits, so no single object can exceed 64 KB.
  • No aligned allocation. posix_memalign (and memalign / aligned_alloc) are deliberately not provided — the Lynx needs no power-of-two alignment, so the admin header was reduced to two bytes and blocks come back at whatever address the allocator yields. Removing them is exactly what lets the raw = p − 2 invariant above hold unconditionally.
  • Allocation failure returns a null pointer but does not set errno to ENOMEM. The memory functions report failure only through their return value; there is no errno-based path.
  • free() accepts only a pointer previously returned by malloc/calloc/realloc (or a null pointer). Interior or fabricated pointers are not tolerated — the word immediately below the pointer is read directly as the block size, with no validation.
  • Not reentrant and not thread-safe, and unsafe to call from an interrupt handler. The free list is plain global state with no locking; the Lynx is single-threaded, but do not call the heap from an IRQ that might interrupt another heap operation.
  • No memory protection. The heap grows up while the C stack grows down toward it (section 5); at run time nothing keeps them apart unless you build with --check-stack. There is no fault or signal — an overrun silently corrupts memory.
  • malloc(0) returns a null pointer. (The C standard also permits a unique, freeable pointer; this implementation chooses null.)
  • _heapblocksize, _heapmemavail, _heapmaxavail and _heapadd are cc65 extensions, not part of POSIX or ISO C.

The following pseudo variables declared in the lynx.h header file do allow access to hardware located in the address space. Some variables are structures, accessing the struct fields will access the chip registers.

MIKEY

The MIKEY structure allows access to MIKEY chip. See the _mikey.h header file located in the include directory for the declaration of the structure.

SUZY

The SUZY structure allows access to SUZY chip. See the _suzy.h header file located in the include directory for the declaration of the structure.

8. Device support

This tree has no loadable drivers at all. Graphics, joypad input and ComLynx serial are each provided as a static, smart-linked library, described below.

8.1. Graphics (TGI)

TGI on the Lynx is a direct-call static library, not a loadable driver: there is exactly one display mode (160×102 in 16 colors) and all drawing is done by the Suzy sprite engine. No tgi_install() call is needed; just call tgi_init(). See LYNX_TGI_DESIGN.md for the design.

The library is implemented as an interrupt driven dual buffering device. To use it as a single-buffer device set draw page and view page to the same value 0 or 1;

Calling tgi_sprite(spr) will display a standard Lynx sprite on screen.

Calling tgi_flip() will do a flip screen (180-degree rotation for left-handed use).

Calling tgi_setbgcolor(bgindex) will set the text background color to the index defined by bgindex. If bgindex is 0 then the background color is transparent.

To set the framerate of the display hardware call tgi_setframerate(rate). The supported framerates are 50, 60 and 75 frames per second. Actually there is no real reason to use anything else than 75 frames per second.

To check if the drawing engine is busy with the previous swap you can call tgi_busy(). It returns 0 if idle and 1 if busy.

To update displays you can call tgi_updatedisplay(). It will wait for the next VBL interrupt and set the draw buffer to the view buffer. The draw buffer is also changed to (drawbuffer xor 1).

You can also enable or disable collision detection by a call to tgi_setcollisiondetection(active). The collision result is located before the sprite structure by default.

In order to reserve memory for the collision detection buffer you need to specify lynx-coll.cfg as the configuration file to the linker.

8.2. Joypad input

There is no loadable joystick driver: input support is a static library function (see LYNX_JOY_SER_DESIGN.md). joy_read() returns all nine inputs in one call: d-pad, A, B, Opt 1 and Opt 2 in the low byte and Pause in bit 8. No installation is required and there is nothing to fail; joy_count() is a compile-time constant 1. Edge detection is done in the application: pressed = now & ~prev.

The extended memory (em), mouse, conio and dbg APIs have been removed entirely: the Lynx has a flat 64 KB address space, no pointing device and no text mode.

8.3. ComLynx serial

There is no loadable serial driver either: the ComLynx code is a static, smart-linked library (ser_open, ser_close, ser_get, ser_put, ser_status). Both directions are interrupt driven through 256-byte ring buffers. ser_close() disables the serial interrupts, stops the baud timer and drops buffered data. The SER_ERR_* codes are renumbered relative to stock cc65: always compare against the macros.

The ComLynx port has Tx and Rx wired together. Every byte is sent to all connected Lynxes. Only one Lynx can send at a time. There is no protocol created for communication. You are on your own.

If the Lynx returns framing error then it is likely that another Lynx is sending data at the same time.

The Lynx can also send a break and receive a break. The Lynx break is recognized if the bit is down for 24 bit cycles or more.

To send a break you just set the break bit. The length of the break depends on how long this bit is down.

The library supports the baudrates:

  • 62500

  • 31250

  • 9600

  • 7200

  • 4800

  • 3600

  • 2400

  • 1800

  • 1200

  • 600

  • 300

  • 150

  • 134.5

  • 110

  • 75

The parity bit supports MARK and SPACE. It also supports EVEN and ODD parity but the parity bit is included in the calculation. Most of us don't want it this way. But there is nothing we can do about it.

The Lynx hardware will always check parity on incoming traffic. Currently the library cannot receive data from standard PCs due to this parity bug. For working with Lynx to Lynx communication use EVEN parity.

To send data to standard PC's use MARK or SPACE as parity setting.

There is always only one stop bit. And the data length is always 8 bits.

We have no handshaking available. Even software handshake is impossible as ComLynx has only one wire for the data.

Both transmit and receive are interrupt driven.

9. Lynx-specific code-generation optimizations

This tree contains a set of 65SC02/Lynx code-generation improvements over stock cc65 2.19. The full design, measurements, and verification plan are in LYNX_CODEGEN_DESIGN.md at the root of the source tree. Summary:

Runtime library fast paths

The hottest runtime routines (pushax, ldaxsp, staxsp, staspidx, pusha, enter) have 65C02 variants using (zp) addressing and PHX/PLX-style instructions, saving 1-4 cycles per call. These routines run on every C stack or pointer access, so the savings apply to nearly all compiled code.

Direct 65C02 emission in the compiler

The code generator emits (zp) indirect addressing for zero-index pointer loads and stores, and STZ for constant-zero stores, directly instead of relying on the peephole optimizer. This mainly benefits unoptimized builds; at -O the peepholes already produced these forms.

Jump-table switches

Dense char-typed switch statements with enough cases are compiled to a JMP (table,x) dispatch instead of a compare/branch cascade. Dispatch cost is constant regardless of the number of cases (measured 76 vs 93 average cycles on a 6-case switch). Word-sized switches keep the cascade.

Self-modifying-code runtime variants

Because the Lynx executes from RAM, memcpy and memset use self-modifying code (guarded by __LYNX__), measured 8-12 percent faster for sizes of 256/512 bytes and up. The SMC macros used are available to your own code as well, see the SMC macro documentation. Note that SMC routines are not reentrant; the same contract as the rest of the zero-page runtime applies.

Suzy hardware multiply and divide

Integer multiply and divide can run on Suzy's hardware math unit instead of software shift-add/shift-subtract loops. The standard *, / and % operators keep the stock software routines; Suzy math is requested per call site with the fork-specific opt-in operators !*, !/ and !% (same precedence, associativity and type rules as their standard counterparts), plus a fused a !* b !/ c that keeps a 32-bit intermediate product to avoid overflow. Small divisors are normalized to cut divide latency. A non-blocking start/poll/harvest variant of the same unit is available through <suzymath.h>; see How the Suzy math functions work in the function reference.

Cycle-cost model

The optimizer carries a per-instruction 65SC02 cycle model alongside the existing size model, so passes can prefer the faster of two encodings instead of guessing. At a speed-biased setting (-Oi, or --codesize above 100) the small incsp1/incsp2 C-stack drops are inlined when the model shows the inline body beats the jsr/rts call overhead, trading a few bytes for speed. At the default size setting nothing changes. This is rarely triggered in practice and is purely an internal optimization; see the design document, section 2.7.

10. Limitations

No Rockwell bit instructions (RMBx/SMBx/BBRx/BBSx)

The compiler and runtime never emit the Rockwell single-bit instructions, even though --cpu 65c02 would assemble them. They are not portable across the Lynx hardware family: the original Lynx (Lynx I) uses a 65SC02 core that omits them — the opcodes decode as NOP-like no-ops, so code relying on them silently misbehaves — whereas the later Lynx II Mikey revision implements the full Rockwell bit set and executes them as intended. Using them would mean either dropping Lynx I support or carrying two execution paths (runtime CPU detection plus duplicated, separately tested runtime routines and peepholes).

The payoff does not justify that cost. The instructions only help single-bit set/clear and test-and-branch on zero-page bytes, a thin slice of the instruction mix, and most C variables are not in zero page. Where the pattern does occur, the TRB/TSB, STZ and BIT instructions available on the shared 65SC02 baseline (and already used by the optimizer) capture the realistic benefit; the only thing they cannot replicate is the fused test-and-branch of BBRx/BBSx, worth roughly 2–3 cycles and 3 bytes per site — a sub-1–2 percent whole-program effect. A single 65SC02 build that runs unmodified on both Lynx I and Lynx II is worth more than that margin. See LYNX_CODEGEN_DESIGN.md section 3 for the full rationale.

11. Cart access

At this point in time there is no support for the cart filesystem yet. I have a lynx-cart-demo example project that uses an interrupt driven display, has support for the cart filesystem and an abcmusic sound module.

At some point in time these may be folded into the tree as supported APIs. For the time being you can create less portable applications using these Lynx specific modules in lynx-cart-demo.
