Compiler bugs

The tracker for wrong-code and wrong-parse bugs in the C compiler: every bug fixed in this fork, and the known bugs still open. Most are inherited from the upstream cc65 2.19 base this SDK forked from.

1. How bugs are found and tracked

The compiler is under a standing correctness audit (design/LYNX_COMPILER_AUDIT_DESIGN.md): every test function is compiled at all four optimization levels (no -O, -O, -Oi, -Ors), executed on the headless GearLynx emulator, and its results are compared across levels and against the same source compiled with a host C compiler. Any disagreement is a compiler bug. The audit combines a directed test corpus (tests/compiler/corpus/), a random-program generator (lynxsmith), and mining of the fixes upstream cc65 made after the 2.19 release (tests/compiler/upstream/FIXES.md).

Every bug on this page has an execution-checked regression test that runs in CI (tests/run.sh). Open bugs live in tests/compiler/corpus/known/ marked known-bug; the harness expects them to fail, and the moment a fix lands it flags the stale marker so the entry moves to the fixed table below in the same change.

e7262013f		 codegen.c
(g_div)		 Signed division by a power-of-two constant (n / 2, n / 8, n / 256…) was strength-reduced to a bare arithmetic shift, which rounds toward negative infinity instead of C’s required truncation toward zero: -7 / 2 gave -4 (must be -3), -300 / 256 gave -2 (must be -1). Inherited from cc65 2.19 (upstream fixed it shortly after that release); found by the audit’s host-oracle on the day the audit went live. The fix adds (2^k)-1 to negative 8/16-bit dividends before the shift; signed 32-bit dividends use the runtime divide. Execution tests corpus/sdiv_pow2.c, corpus/sdiv_bounds.c; upstream classification in tests/compiler/upstream/FIXES.md

3. Known open bugs

Confirmed present and not yet fixed. Each has an expected-to-fail regression in tests/compiler/corpus/known/ and an upstream fix reference in tests/compiler/upstream/FIXES.md. Until they are fixed, avoid the affected shapes in game code:

ComponentBugWorkaround
comparison codegen signed char compared with an unsigned constant can give the wrong truth value: sc > 100u, sc == 0x80u… (corpus/known/scharcmp_uconst.c) Cast explicitly: (int)sc > 100
comparison codegen signed long compared with a smaller unsigned type can give the wrong truth value: -2L < 40000u comes out false (corpus/known/slongcmp_mixed.c) Cast the unsigned operand to long first
parser A subscript, call, or member operator directly after a postfix ++/-- is rejected with a parse error: p++[0] does not compile (noted in corpus/upstream_shapes.c) Parenthesise or split: (*p++), or v = p[0]; ++p;
