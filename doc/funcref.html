1. Introduction

cc65 is a C compiler for 6502-based systems. It implements a subset of the ISO C standard plus additional functions specially crafted for 6502 systems or just some of the supported machines. This function reference describes the available functions together with any limitations.

For an overview of which standard functions are missing or limited on this target, see section 5. Functions that are not listed here or in the header files behave as defined in the C standard.

Note: Standard C functions are listed here, but not described in detail. Because those functions behave identically on all standard-compliant systems, they are described in any book covering standard C.

3.12. _sys

Function

Call a subroutine passing register values.

Header

6502.h

Declaration

void __fastcall__ _sys (struct regs* r);

Description

The function will call the subroutine at the address specified in the pc member of the passed regs structure. All registers and the CPU flags are set to the values given in the regs structure. On return from the subroutine, the new values of the registers and flags are stored back overwriting the old values.

Notes

  • Bits 4 and 5 of the flags value in the regs structure are ignored when calling the subroutine (they are unchanged from their current values).

  • The function is only available as fastcall function, so it may only be used in presence of a prototype.

Availability

cc65

Example

None.

3.21. atexit

Function

Register an exit function.

Header

stdlib.h

Declaration

int __fastcall__ atexit (void (*exitfunc) (void));

Description

atexit registers the function pointed to by exitfunc as an exit function. Exit functions are called when the program terminates, they are called in LIFO order (the last function registered is called first). atexit returns zero on success and a nonzero value on failure.

Notes

  • A maximum of 5 exit functions can be registered.

  • There is no way to unregister an exit function.

  • The function is only available as fastcall function, so it may only be used in presence of a prototype.

Availability

ISO 9899

See also

abort, exit

Example

None.

3.83. set_irq

Function

Set the C level interrupt request vector to the given address.

Header

6502.h

Declaration

void __fastcall__ set_irq (irq_handler f, void *stack_addr, size_t stack_size);

Description

set_irq allows a user program to handle interrupt requests (IRQs) within the program code by letting the vector point to a user written C function. The runtime library installs a small stub that saves the zero page registers used by the C runtime before calling the handler function and restores them after the handler function returns. Additionally the stub temporarily switches the C runtime stack to the stack area provided as parameter. If the handler function was set up to handle a "private", "exclusive" interrupt request source it must return the value IRQ_HANDLED if and only if it has verified that the current interrupt request actually stems from that source. In all other cases it must return the value IRQ_NOT_HANDLED.

Notes

  • The function is only available as fastcall function, so it may only be used in presence of a prototype.

  • The stub saves the registers and zero page locations used by the C runtime and switches to the provided stack area. As a consequence, there is some runtime overhead, but it it is safe to execute C code, even if other C code was interrupted. Be careful however not to call C library functions, and do not enable stack checks for the handler function or any other function called from it.

  • The interrupt vector is reset on program termination, so it's not strictly necessary to call reset_irq as a part of your clean-up when exiting the program.

Availability

cc65

See also

reset_irq

Example

None.

3.86. snprintf

Function

Format data into a string buffer, with a size limit.

Header

stdio.h

Declaration

int snprintf (char* buf, size_t size, const char* format, ...);

Description

snprintf formats its arguments according to format and writes the result into buf, storing at most size bytes including the terminating '\0'. The return value is the number of characters that would have been written had the buffer been unlimited, not counting the terminating '\0'; so a return value of size or greater indicates that the output was truncated.

Notes

  • The conversions c d i n o p s u x X are supported, together with flags, field width, precision and the h l z t j L length modifiers. Because cc65 has no floating-point support, the floating-point conversions (e E f F g G a A) are not available.

  • If size is zero, nothing is written into buf (which may then be NULL), but the return value is still computed.

  • size must not exceed INT_MAX; a larger value sets errno to ERANGE and returns -1.

4. How the Suzy math functions work

The Suzy chip contains a hardware multiply/divide unit that runs concurrently with the 65C02. The synchronous !*, !/ and !% operators already use it, but they spend the whole operation in a poll loop, throwing that concurrency away — a divide can burn roughly 44 to 100 CPU cycles doing nothing while the unit works. The functions in suzymath.h expose the same hardware as a non-blocking, intrinsic-level API so those cycles can be spent on useful work instead.

4.1. The hardware unit and the start / poll / harvest model

Each operation is split across three steps. A *_start call writes the operand registers and triggers the unit, then returns immediately. The unit computes while the CPU runs ahead. suzy_math_busy reports whether the unit is still working by testing the MATHWORKING bit (bit 7 of SPRSYS at $FC92). Finally a matching *_result call harvests the registers, applies any sign fixup and returns the value. The single math unit means the model is a simple three-state machine — idle, running, done — and that exactly one asynchronous operation may be in flight at any time, process-wide.

The typical use, and the one worth writing, is the divide:

#include <suzymath.h>

suzy_udiv_start(distance, speed);   /* start the slow divide            */
update_score();                     /* ~80 cycles of NON-Suzy work      */
ticks = suzy_udiv_result();         /* unit is already idle: free read  */

Modulo and fused multiply-divide are two-phase: only their divide overlaps the interleaved work, and the trailing multiply/subtract (modulo) or the multiply and inter-phase poll (muldiv) run inside the start or result call. The fused forms therefore take all three operands at start, because the divisor must be in the registers before the divide is triggered.

4.2. Why only the divide is worth overlapping

The economics decide which operations have a useful async form. A multiply finishes in about 11 cycles — before the next few instructions retire — so the call and return overhead exceeds anything that could be hidden; the multiply functions exist only for symmetry and are documented as rarely worth it. A divide takes long enough (up to ~100 cycles) that a real chunk of unrelated work fits in its shadow, which makes suzy_udiv_start the headline feature. Modulo and fused muldiv are built on a divide, so they hide that divide but still pay a short, fixed tail when the result is harvested. The unsigned divide is the cleanest case of all: it carries no sign or operand state across the gap and needs no SPRSYS setup.

4.3. Why they are safe to use

Safety rests on three properties. First, early or late harvest cannot return garbage. Every *_result routine begins with the same defensive poll the synchronous operators use, so harvesting before the unit finishes simply blocks until it does — the async path degrades to a synchronous operation rather than reading a half-computed value. suzy_math_busy lets you skip that spin when you have real work to interleave, but the spin is always the floor. Harvesting late, or never, leaves a stale result in the registers that is harmlessly overwritten by the next start.

Second, the results are verified equal to the synchronous operators. The async routines share the operand-placement code and the hardware contracts of !*/!//!%: divide-by-zero yields $FFFF, signed results get the same sign fixup, and a host model of all seven routines was checked against the synchronous reference with zero mismatches across thousands of corner cases (including narrow divisors, the 256 boundary, and the 32-bit muldiv product). Signed state that must outlive the gap is parked in a small dedicated memory block, not the general runtime scratch the overlapped C code may reuse.

Third, the one new rule is auditable. Because you are voluntarily holding the math unit open across a span of your own code, that span must touch no Suzy state at all: no TGI drawing, no sprite launch, no other Suzy math (operator or async start), and no SPRSYS write, because the sprite engine shares the very same math registers. Every async use is an explicit suzy_*_start / suzy_*_result pair, so a reviewer can scan the code between a pair for forbidden Suzy use by eye or by grep. The usual operator contracts also carry over: the routines are not interrupt-safe, and the sprite engine must be idle while a math operation runs.

5. What is not in the library

The C library contains a large subset of the ISO C library. Functions are usually missing in areas where there is no support on a ROM-based, console-less 6502 system such as the Lynx — wide-character sets are an example. If a function is not mentioned below and is not flagged in its per-function entry, expect it to be available and to behave as defined in the C standard.

5.1. Functions that are not available

  • tmpfile/tmpnam.

  • system and the non-standard exec: the Lynx has no shell or command processor. To run another cart image, use lynx_load/lynx_exec from <lynx.h>.

  • All functions that handle floating-point numbers in some manner.

  • The ldiv function (cc65 currently is not able to return structs by value with a size not equal to 1, 2, or 4 bytes).

  • All functions handling wide-character strings.

  • Signals and all related functions (having SIGSEGV would be cool. :-)

  • setbuf/setvbuf.

  • getenv/putenv: there is no environment on the Lynx, so these functions are not provided.

  • time: there is no real-time clock, so the time function is not available. The other functions from <time.h> are available.

5.2. File I/O is read-only

File I/O on the Lynx is read-only, because the cart is ROM and there is no character console:

  • There is no FILE object, so none of the byte-stream functions are provided. The output family is absent — fopen/freopen/fclose, fwrite, printf/fprintf/vprintf/vfprintf, putchar/puts/fputc/fputs and perror — and so is the input FILE family: fread/fgets/fgetc, fscanf/scanf/vfscanf/vscanf, fseek/ftell/fgetpos/fsetpos/rewind, getchar/gets/ungetc, feof/ferror/clearerr/fflush and fdopen/fileno. For on-screen text use tgi_outtext from <tgi.h>.

  • The only <stdio.h> functions that remain are the in-RAM string routines: sprintf/snprintf (and vsprintf/vsnprintf) format into a buffer, and sscanf (and vsscanf) parses one. Because cc65 has no floating-point support, the floating-point conversions (e E f F g G a A) are absent from all of them, and sscanf additionally rejects the wide-character conversions (S C). To stream raw bytes from the cart, use read()/lseek() on a handle from openn() (see <unistd.h> and <lynx.h>).

  • remove/rename and the name-based open/creat/close/write are not provided: cart files are ROM and are addressed by number, not by name.

5.3. Functions that are limited

  • strcspn/strpbrk/strspn: these functions have a length limitation of 256 for the second string argument. Since that string gives a character set, and there are only 256 distinct characters, that shouldn't be a problem.

  • locale: there is no locale other than the "C" locale. The native locale is identical to the "C" locale.

5.4. Extra limits when inlining with -Os

Some more functions are limited if inlined versions are requested by using the -Os command-line option:

  • The strlen function works for only strings with a maximum length of 255 characters.

  • The isXXX character classification functions from <ctype.h> will give unpredictable results if the argument is not in character range (0..255). That limitation may be removed by #undef'ing the function name (when using -Os, the functions are actually macros that expand to inline assembly code, but the real functions still are available if the macro definition is removed).

5.5. Removed driver APIs

The em (extended memory), mouse, conio and dbg APIs that ship with the stock cc65 library are not part of this tree: the Lynx has a flat 64 KB address space, no pointing device and no text mode, so those headers and their drivers have been removed entirely. Text output goes through the TGI bitmap-font functions instead (see tgi.html). The generic loadable joystick driver is likewise replaced by a small static implementation; a single joy_read call returns every input the console has (see joystick.h and design/LYNX_JOY_SER_DESIGN.md).
