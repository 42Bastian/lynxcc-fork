Sample programs

A guide to every program in the examples/ directory of the Atari Lynx tree.

Each sample is a single, self-contained C file that builds to a .lnx cartridge image. They double as worked examples of this fork’s Lynx-specific features — the static Lynx graphics, joystick and serial libraries, and the Suzy hardware-math operators !* !/ !%. Build any one with the command shown, or run make in examples/ to build them all. Each entry carries a screenshot captured by booting its .lnx on the headless GearLynx emulator (tests/emu/gearlynx).

standaloneown Makefile

The barest self-contained project in the tree — the one to copy out and start from nothing.

  • Unlike every other sample, it is not built by the shared examples/ Makefile: it carries its own one-line cl65 build rule, so the directory works after you copy it out of the SDK tree and rename it.
  • Does only the minimum to put text on screen: gfx_init() brings up the static Lynx graphics library (no driver to load), gfx_setdefpalette() loads the built-in default palette, and one gfx_clear() / gfx_outtextxy() / gfx_updatedisplay() pass draws the message.
  • No game loop and no input: it renders a single frame and holds it, so the whole program fits in one screenful of C.

Games

breakout.cSuzy math

Single-file Breakout, built to exercise the fork's Suzy hardware math in real game code.

  • Paddle deflection, brick-grid hit testing and score formatting all run on Suzy's 16×16 multiply and 32/16 divide (!* !/ !%) instead of software loops.
  • The whole scene — 32 bricks, paddle and ball — is one SCB chain drawn with a single gfx_sprite() call; dead bricks are skipped with the SKIP bit.
  • All math sites stay in the main loop (never in IRQ), honouring the Suzy math contract.
Controls
Pad left/right moves the paddle, A serves / restarts.

invaders.ccolour + sound

Single-file Space Invaders — a companion to breakout that adds colour and audio.

  • Coloured enemies: every invader shares one sprite image; its row colour comes from the SCB penpal, and the RGB behind each pen is repainted from a 12-entry rainbow LUT so colour flows down the formation with zero extra sprite data.
  • Music + effects: channels C and D play the two-voice Space Invaders theme as compiled snd-engine streams (invtheme.s, extracted from the reference cartridge as interlocking pattern/loop sequences over a shared attack envelope); the streams self-loop while the interrupt walks them. Channels A and B stay hand-driven for laser and explosion noise (death/UFO share channel A) with per-frame volume envelopes.
  • Suzy math lays out the grid, does the hit-test lookup, paces the march and formats the score.
Controls
Pad left/right moves the cannon, A fires / restarts.

lander.cphysics

A complete lunar-lander — MOON LANDER — with Newtonian flight, a fuel budget, randomised terrain and a full title menu, instructions screen and land / crash prompts.

  • Rotate the module and fire the descent engine against gravity; touch down slow, upright and on a flat pad to score, with narrower pads worth more. Position and velocity are 7.7 fixed point; a 24-entry sin/cos table turns the ship's heading into a thrust vector, so no trigonometry runs on the 6502.
  • The lander and its exhaust are pre-rendered rotation sprite sheets — 24 headings each, sliced from lander.pcx and flame.pcx by sp65 --sprite-sheet — so drawing a heading is one table index. Terrain columns, pads and stars are one solid sprite stretched and recoloured through each SCB pen palette, and the whole scene is one gfx_sprite() chain per frame. The HUD read-outs and landing score use the Suzy operators !* !/ !% in the main loop.
  • Four-channel audio through the snd engine: a calm menu loop and a driving melody-plus-bass game theme (compiled by abccc from the committed .abc tunes), a looping engine roar from the sfx pack while the thruster burns, and one-shot touchdown / crash blips.
Controls
Pad left/right rotate the lander, A fires the engine (burns fuel), Pause pauses. On the menu, Up/Down choose and A selects; on the instructions screen, B returns; after a landing or crash, A flies again and B returns to the menu.

raycaster.cscaled sprites

A Wolfenstein-3D-style raycaster that leans on three things Lynx hardware makes cheap.

  • Hardware sprite scaling as a fill primitive: each vertical wall slice is one 2×1 solid sprite stretched by the SCB's vsize field — 80 scaled sprites paint the whole 3D view with no per-pixel plotting.
  • Suzy hardware divide (!/) powers the DDA delta-distances and slice-height divides in the main loop.
  • The 16-entry 12-bit palette gives free directional shading: N/S faces use a darker pen than E/W faces of the same wall.

sybil.cplatformer

A single-screen Super-Mario-Bros.-style platformer starring Sybil.

  • Multi-colour 16×16 hardware sprite with true transparency: Sybil uses an identity SCB penpal (pixel value N → pen N), so her ten colours come straight from the 12-bit palette and pixel value 0 is the transparent pen of a TYPE_NORMAL sprite. Idle / run / jump animation just swaps the data pointer; left-facing frames are pre-mirrored arrays.
  • Sprite scaling as a fill primitive: every platform is one 8×8 solid block sprite stretched to size with the SCB hsize/vsize fields — a brown body plus a green cap, no tile map.
  • Direct Mikey audio (no driver): channel A = jump, B = coin / stomp, C = win & game-over jingles, D = ouch. Suzy math (!* !/ !%) formats the score and does coin scoring, all in the main loop.
Controls
Pad left/right runs, A jumps; A restarts after GAME OVER. Collect every coin to clear the level; stomp enemies from above, avoid them from the side.

tetris.cpuzzle

A complete falling-block puzzle — TETROIDS — with a title menu, an instructions screen and the seven tetromino shapes.

  • A menu (Start / Instructions), a controls screen, gameplay and a game-over prompt, all driven by one state machine in the main loop.
  • The whole scene — grey well frame, every settled cell, the falling piece and the next-piece preview — is a single SCB chain drawn with one gfx_sprite() call. One 4×4 block image paints all seven piece colours plus the frame purely through per-SCB pen palettes (compare breakout.c).
  • Wall-kick rotation, hard drop and a level curve that shortens the drop interval as rows clear. Score formatting and the level-scaled line award use the Suzy hardware operators !* !/ !%, all in the main loop.

muldivtest.ccorrectness

An on-hardware correctness test for the Suzy math operators !* !/ !%.

  • Six sweeps over a corner-value table compare each Suzy result against an independent software reference, in signed and unsigned variants.
  • Divisors 1, 127, 255 (narrow), 256 (boundary) and wide values exercise both sides of the small-divisor normalisation shift.
  • Shows pass/total per sweep and the first failing case; “ALL PASS” means every case matched.

spritetest.cbuild-time packing

The offline counterpart to packtest: sprite data packed at build time by sp65, not at runtime.

  • The Makefile runs the in-tree sp65 sprite converter (-c lynx-sprite,mode=packed and mode=literal) over heart.pcx to emit two C headers, which the sample #includes and drops straight into an SCB data pointer — no runtime packer in the ROM.
  • Both encodings of the same 16×16 image are drawn side by side at 3× scale with one identity-penpal SCB_REHV_PAL; only the PACKED bit of SPRCTL1 and the data pointer differ, so the columns must be pixel-identical while the packed block is the smaller asset.
  • heart.pcx keeps pen 0 along both side edges, so no scan line ends on an odd pen value and Suzy's last-pixel bug needs no pad byte; the PCX itself is reproduced by heart.pcx.py.
Build
make -C suzy/spritetest (regenerates the headers via sp65 first)

spritesheet.csprite sheet

Sprite sheets the easy way: sp65's --sprite-sheet driver turns one image into one indexable frame table.

  • One source image, sheet.pcx (a 4-frame, 16×16 bouncing-ball strip generated by sheet.pcx.py), is sliced in a single sp65 --sprite-sheet call that emits one header: a sheet_anim_data[] blob plus a generated sheet_anim[] pointer table and a sheet_anim_COUNT define.
  • Animating is just scb.data = (unsigned char *)sheet_anim[frame] — no per-frame files, no hand-written table.
  • The frame data is byte-for-byte identical to the manual --slice chain in spriteslice.c; only the packaging differs (verified on GearLynx, framebuffer read-back).

spriteslice.cslice + pop

Sprite sheets the manual way: sp65's --slice/--pop chain, no special tooling.

  • Reads the same sheet.pcx once and dices it into four standalone headers (frame0…frame3) in one sp65 run, popping back to the whole image between cells.
  • Because each header is an independent const unsigned char frameN[] sprite, the program gathers them into its own frames[] table and tracks the count itself — the hand-work the driver in spritesheet.c removes.
  • Draws the identical bouncing ball, proving the two routes produce the same frames; the right choice when you only want a few frames or want per-frame control.

sprpcktest.csprpck BMP + SPS

The sprpck counterpart to spritetest: sprites packed offline from the two input formats sp65 cannot read — a Windows BMP and a plain-ASCII SPS file.

  • The Makefile runs the vendored sprpck (tools/extern/sprpck) twice: -t6 -s4 logo.bmp logo.spr packs an indexed BMP, and -t2 -i016016 -s4 icon.sps icon.spr packs the ASCII star in icon.sps (one hex digit per pixel, space = pen 0).
  • sprpck writes the packed sprite as a raw binary .spr, not a C array, so sprpckdata.s pulls both in with ca65 .incbin and the C side reaches them as extern arrays — the idiomatic way to link sprpck output.
  • One SCB with a shared 16-pen palette draws both: the crystal in the BMP's compacted pens 1–3 (sprpck also emits a matching logo.pal), the star in its SPS pens 6 and 8. Default sprpck output is PACKED, so the SCB carries the packed SPRCTL1 bit.

spritefx.ctransforms + action point

An interactive tour of Suzy's four sprite transforms — hsize, vsize, stretch and tilt — and of where a sprite's action point sits.

  • One shape (cube / crystal / star / ball) is drawn around a fixed on-screen anchor and the selected transform is animated back and forth, so the picture visibly grows or shears outward from the anchor while the anchor pixel never moves. A bright magenta cross (a separate marker.pcx sprite whose own action point is its centre) is drawn at that anchor every frame to make the pivot unmistakable.
  • The action point is baked into the sprite data by sp65, not the SCB, so the Makefile compacts each shape five times — ax,ay at the four corners and the centre — and the program keeps a 4×5 table of the results. Cycling the action point swaps only the data pointer; every SCB scale field stays byte-for-byte identical, yet a scaled or sheared shape lands somewhere else because it now pivots about a different pixel. The centre variant is a true four-quadrant sprite, the case the hsizeoff/vsizeoff $007F correction (set once at start-up) exists to serve.
  • The four shapes use disjoint pen ranges baked in by spritefx_shapes.py, so one 16-entry palette and an identity SCB penpal colour all of them; sp65 picks each shape's bit depth from its highest pen index and the program reads the generated _COLORS define back to set the matching SPRCTL0 depth.
Controls
Pad selects the live transform (LEFT hsize, RIGHT vsize, UP stretch, DOWN tilt), A / B cycle the shape, OPTION 1 cycles the action point.
Build
make -C suzy/spritefx (regenerates the 20 shape headers + marker via sp65 first)

suzyasyncbench.casync speed

An honest speed benchmark for the asynchronous Suzy math API.

  • For three workload sizes (no / light / heavy work) it times SOFT (software divide), SYNC (blocking Suzy) and ASYNC (overlapped Suzy) per divide.
  • ASYNC runs unrelated CPU work in the shadow of the divide; the crossover where it overtakes SYNC is the whole point — with no overlap work it is honestly slower.
  • Every loop cross-checks SOFT, SYNC and ASYNC so a speed win is never a correctness loss.

packtest.cpacked vs literal

On-hardware proof that Suzy's PACKED (RLE) sprite encoding is interchangeable with the LITERAL encoding, at every depth.

  • For each of the four Suzy depths (1/2/3/4 bpp) it draws the same 16×16 source image twice at 1× scale: a LITERAL copy as the control and a PACKED copy built at runtime by an in-program pack_line() encoder.
  • The source is deliberately adversarial — a vertical rainbow on top (every pen value, all adjacent pixels distinct: exercises literal packets and the value→pen map) over solid horizontal bands (exercises RLE runs).
  • Identity penpal and a TYPE_NORMAL sprite, so pixel value v draws pen v and value 0 is transparent; the literal copy carries the per-line pad byte and the packed copy's 00000 terminator supplies the same trailing slack for Suzy's last-pixel bug. If packing is correct the two columns are pixel-identical (verified on GearLynx, framebuffer read-back).

collision.ccollision buffer

Demonstrates Suzy's hardware collision buffer and the per-sprite collision depository — the only collision facility the Lynx has.

  • Four fixed target blocks carry distinct collision numbers 1–4; a white player block sweeps across them. Targets are drawn first so they lay their numbers into the collision buffer, then the player last — as it paints, Suzy reads those numbers back and drops the highest into the player's depository byte.
  • The depository lands one byte in front of the SCB (gfx_init sets COLLOFF = −1), so a wrapper struct with a leading coll byte reads which target was struck with no per-pixel testing in C; the hit target flashes and a HIT TARGET n read-out shows the value.
  • The one example in the tree that links with lynx-coll.cfg instead of the default config, because the collision buffer must be reserved in RAM; gfx_setcollisiondetection(1) turns detection on and makes gfx_clear() wipe both buffers each frame.
Controls
The player auto-sweeps; the d-pad steers it (up/down to change row, left/right to nudge).

palette.cpalette

System

poweroff.csoft power-off

Turns the Lynx off in software with poweroff().

  • Clears bit 1 of SYSCTL1 (0xFD87), the regulator's soft on/off line, which powers up as 1; clearing it disconnects the system from the battery — the same mechanism that auto-powers-off an idle unit.
  • The call masks interrupts and does not return on real hardware. A real game would save state to the EEPROM first; this demo keeps to the one call so the mechanism is clear.
  • A |/-\ spinner turns as a running-activity indicator: while it animates, power is on (SYSCTL1 bit 1 is still 1). It stops the instant poweroff() halts the CPU.
  • Emulators generally do not model the regulator soft-off, so under emulation the screen simply freezes on the “powering off” frame instead of switching off.
Controls
A powers the unit off.

cl65 -Ors -o poweroff.lnx poweroff.c

Memory

heaptest.cheap correctness

On-target verification that the heap allocator's 2-byte block header behaves correctly.

  • Runs 17 checks across the public API — malloc, calloc, realloc, free, _heapblocksize, _heapmemavail, _heapadd — covering exact sizing, in-place vs moving realloc, coalescing and full reclamation.
  • Cross-checks the library against direct memory inspection: the raw size word stored just below each user pointer, the runtime heap variables (_heaporg / _heapptr / _heapend) and the free-list head, confirming the raw block is always (user − 2).
  • Draws a colour-coded grid — each test green (OK) or red (X) — with a PASS k/17 summary and the first failing test; the heap variables are shown live in hex.

zeropage.czero page

Places C globals in the zero page with the __zeropage attribute.

  • Three counters are declared __zeropage (from <zeropage.h>), so the compiler emits them into the ZEROPAGE segment and addresses them with the fast 2-byte zero-page opcodes — inc _frame assembles to E6, not the 3-byte absolute EE.
  • No companion assembler file and no #pragma zpsym: a single C declaration both defines the storage and marks the symbol.
  • The Lynx graphics text harness shows the live counters; A and B bump the zero-page presses counter up and down.
Controls
A counts up, B counts down; the frame counter free-runs.

Storage

sdcardls.cSD/GD flash cart

Lists the root directory of a RetroHQ Lynx SD / GD flash cartridge using the sdcard_gd_* API.

  • Wakes the cart MCU with sdcard_gd_init(), opens the card root with sdcard_gd_opendir("/") and walks it with sdcard_gd_readdir(), printing each 8.3 name and marking sub-directories in green.
  • The opt-in lib/lynx-sdcard-gd.lib is auto-linked by cl65 (no -l flag) via the SDK manifest, exactly like the audio and compress libraries.
  • Only does anything on real hardware with an SD card inserted: in the emulator there is no cart-MCU to answer the FIFO handshake, so the capture shows just the title while the directory call waits. See SD / GD flash cart for the protocol and the on-card layout.

Multicart

multicartmenu loader

A single .lnx that bundles a menu and three independent game ROMs; picking one loads it over the top of the menu and runs it.

  • The menu and each game are separate, self-contained programs built as BLL objects (cl65 -C lynx-bll.cfg); lnx multicart writes a lynxdir layout and lynxdir stitches them into one bootable cart.
  • multicart_run(n) hands off from the menu to game n: it stops the frame timers, blanks the palette, copies a small relocatable loader to $0040 and jumps to it; the loader pulls that game off the cartridge by its directory number and starts it.
  • Launching a game overwrites the menu, so there is no way back without a reboot — one game per power-on, as the LynxJam multicart worked on hardware.
Controls
Up/Down move the cursor, A (or B) launches the selected game.
