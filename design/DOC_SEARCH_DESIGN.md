# Documentation quick-jump search palette

## Goal

Let a reader search the whole doc set from the top bar and jump straight to a
page or a specific section, without a server and without a per-page search box.
This complements the shared chrome described in `design/DOC_STRUCTURE_DESIGN.md`.

## Constraint

The docs open from `file://` with no build server, so a runtime `fetch()` of
the other pages (to index their text) is blocked by the browser. The search
data must therefore already be present in a loaded asset. Full body-text
indexing of every page would be large; section headings are the high-value,
compact target (720 anchored headings, ~15 KB of text), so the palette searches
**page entries + section headings**, not full prose.

## Design

Everything lives in `doc/doc.js`, injected on every page by the existing
`<site-nav>` element; no page markup changes.

### Data

- **Page entries** are derived at runtime from the nav links already in
  `TOPBAR_HTML` (label, description, href) — never duplicated.
- **Section entries** come from `SEARCH_INDEX`, a generated array of
  `[page, anchor-id, heading-label]` rows embedded in `doc.js` between the
  markers:

  ```js
  // === SEARCH_INDEX — generated by `make doc-search-index`; do not hand-edit ===
  var SEARCH_INDEX = [ ["ca65.html","sect-2-1","2.1. Command line options"], … ];
  // === END SEARCH_INDEX ===
  ```

  Keeping the index inside `doc.js` (rather than a separate asset) means no new
  file to ship, install or zip — the chrome and its index travel together.

### Generation

`doc/gen-search-index.py` harvests every `<h2|h3|h4 id="…">` from `doc/*.html`,
strips inner tags (e.g. funcref's `<code>`), unescapes entities, and splices the
array back into the fenced region of `doc.js` — leaving all hand-written code
untouched. `make doc-search-index` runs it; `make doc-search-index-check`
runs it in `--check` mode and fails if `doc.js` would change.

### Palette behaviour

The top bar carries a magnifier button (`#docSearchBtn`); `Cmd/Ctrl-K` toggles
the palette and `/` opens it (ignored while typing in a field). The overlay is a
centered modal: substring filter, ranked so page/title and prefix matches sort
above mid-string section matches; each row shows a kind badge (`Page` / `§`),
the title, and a breadcrumb (the section's page label or the page's
description). `↑`/`↓` move, `Enter` navigates to `page.html#id`, `Esc` or a
backdrop click closes. Styling uses the theme CSS variables in `doc.css`
(`.doc-search*`, `.ds-*`), so it works in both light and dark themes.

## Maintenance rule

The `SEARCH_INDEX` block is **generated**. Any change to section headings — add,
rename, remove, or re-anchor — must be followed by `make doc-search-index`, in
the same pass, per the repo's docs-in-sync rule (`CLAUDE.md`). Do not hand-edit
the array. `make doc-search-index-check` guards against a stale index in CI.

## Trade-off

Section search is heading-level, not full body text. That keeps the embedded
index small and the whole feature build-light (one Python splice, no client
search library), while still covering the structured, linkable parts of the
docs. Full-text would require either a much larger embedded blob or the
`fetch()`-based approach that `file://` disallows.
